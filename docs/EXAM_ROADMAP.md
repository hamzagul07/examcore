**Missing metadata that limits trust (founder should know):**

- No prerequisite graph. Lessons have no `prerequisites` field; syllabus trees give parent → leaves in order (IB trees have no parents at all). The Roadmap uses syllabus order as a soft scoring hint only, says so in low-confidence copy ("Listed before … in the syllabus, so it's worth doing first"), and never gates a task on it.
- Indexed-paper frequency exists for five Cambridge subjects only, and only since May/June 2024 (no 2021–2023 data; Oct/Nov 2025 largely untagged; 9609/9706 have 1–3 tagged papers and must emit nothing). Every other subject (all IB, Edexcel, AQA, AP, the other 22 Cambridge) gets "on the syllabus" evidence, never a frequency claim.
- Per-paper topic map: syllabus leaves carry a `paper` label but in inconsistent forms ('P1'…'P6', 'P1_P2', 'P1/P2', 'AS'/'A Level', IB paper names). `lib/plan/paper-match.ts` normalises them; where a leaf cannot be matched to the chosen component no `nearest_paper` evidence is emitted.
- Curriculum importance is uniform: no tree carries a core/option flag (IB trees have a `paper` label per leaf and `parents: []`, nothing about AHL). `coreWeight` is 1 everywhere and `core_syllabus` evidence is never emitted; the field exists so authors can refine it later without touching the engine.
- Exam *times* and components are not on the profile; the wizard collects them and the plan stores them.

## 2. Decisions

1. **Evolve `study_plans`, keep every consumer working.** New columns are additive; the plan JSON gains optional fields; `PLAN_VERSION = 3` triggers the existing "rebuild, your ticks stay" notice for v2 plans. The dashboard card, check-in email, .ics, report script and `PATCH {day, done}` keep reading v2 and v3 alike.
2. **Modes replace preparedness in copy, not in storage.** `foundation | balanced | polish` are stored in a new `strategy` column and the plan; `preparedness` keeps its existing check constraint and is derived (`MODE_TO_LEGACY_PREPAREDNESS`); a v3 plan stores both.
3. **Deterministic engine; AI explains only.** Scoring, feasibility, placement and replans are pure functions of the snapshot in the plan (`lib/plan/priority.ts`, `feasibility.ts`, `availability.ts`, `task-actions.ts`). No LLM in the schedule path.
4. **Tasks are the unit, days are the frame.** Each work block becomes a `RoadmapTask` with a stable id, type, category, objective, evidence and a suggested clock time. Per-task state lives in `study_plans.task_state`; day ticks stay in `done_days`.
5. **Time of day is placement, not a second capacity model.** Capacity per date = min(stated minutes, free minutes inside preferred windows after commitments and no-study spans). Blocks are laid into the free intervals with the chosen session length and break rhythm. Work and breaks are laid into 80 % of capacity (wall-clock); the remainder is time in hand, shown as a `buffer` block only when ≥ 10 minutes and never counted as work.
6. **Evidence or silence.** `EvidenceItem` has a source and a confidence; "Set in n of the N sittings MarkScheme has indexed" is only emitted with a `stat` (source `indexed_papers`, never "verified" — tags are classifier output). Nothing in copy predicts an exam.
7. **Replan is local and reversible.** "Replan today" rebuilds the remainder of today from the plan's own topic pools, protects done/pinned/started tasks, writes a diff, and keeps a ~5 KB day snapshot for one-tap undo. Undone tasks never stack onto tomorrow: the lazy rollover defers at most one task, once, into the next study day's time in hand, and only if it fits; otherwise it returns to the pool with a calm line.
8. **No fifth tab.** Surfaces: dashboard hero, Study Mode chip, /mark post-result card, check-in email deep links, Progress and Settings links (already there).

## 3. Data model (migration `20260917_roadmap_v3.sql`)

`study_plans` gains: `strategy text check (strategy in ('foundation','balanced','polish'))`, `algorithm_version int`, `revision int default 1`, `feasibility_state text`, `input_snapshot jsonb`, `task_state jsonb default '{}'`, `pools jsonb` (topic priorities per subject — read only by replan/swap/rollover, never sent to the client whole), `undo jsonb` (one day's snapshot), `today_summary jsonb` (materialised on every write), `last_rolled_date date`, `reminder_time text`, `quiet_hours jsonb`, `notify_backoff int default 0`, `checkins_unopened int default 0`. The `preparedness` check is NOT widened; the service writes the legacy code beside `strategy`.

New table `study_plan_events` (service-role only, RLS on, grants revoked, listed in `audit_client_grants()`): `id, user_id, task_id, event_type, subject_code, topic_code, task_type, plan_generated_at, planned_minutes, actual_minutes, feel, reason, revision, meta jsonb, created_at`, indexed `(user_id, created_at desc)`. This is the TaskEvent + PlannerEvidence record; rationale snapshots ride in the plan JSON per task.

Mapping to the requested model: Roadmap ≡ `study_plans` row; RoadmapExam ≡ `plan.exams[]`; AvailabilityBlock ≡ `plan.availabilityDetail` (commitments, windows, no-study) + `blocked_dates`; TopicState ≡ derived at build from `attempts`, `lesson_recall`, `review_schedule` + `input_snapshot.selfRatings`, persisted as `plan.pools[subject][]` (TopicPriority with signals); RoadmapTask ≡ block + `RoadmapTaskFields`; TaskEvent ≡ `study_plan_events`; PlannerEvidence ≡ `task.why[]`.

## 4. API

- `POST /api/plan` — v3 body (`RoadmapBuildRequest`); `preview: true` returns `{ plan, feasibility }` without saving. Legacy v2 bodies still build.
- `GET /api/plan` — `{ plan, done, taskState, evidence }`.
- `PATCH /api/plan` — `{ day, done }` unchanged.
- `PATCH /api/plan/task` — `TaskActionRequest` (carries `revision`; 409 `{ error: 'stale' }` on mismatch; repeats are no-ops); returns `DayMutationResponse` (one day, not the plan); writes a `study_plan_events` row after the update lands.
- `POST /api/plan/replan` — `ReplanRequest` (`date`, `nowMinute`, `revision`; 409 when `date` is not the plan's today) → `DayMutationResponse`.
- `POST /api/plan/undo` — restores the single-level day snapshot → `DayMutationResponse`.
- `GET /api/plan/today` — `RoadmapTodaySummary` from the materialised `today_summary` (recomputed only when its date is stale), `Cache-Control: private, no-store`; runs the lazy rollover first. For the Study Mode chip, /mark and notifications.
- `GET /api/plan` — also runs the lazy, idempotent rollover when `last_rolled_date < today`.

### What was implemented

**Engine (pure, client-safe, `lib/plan/`).** `availability.ts` turns `RoadmapAvailability` into per-date capacity (min of stated minutes and free window minutes after commitments, no-study spans and exams), lays a day into work slots, breaks and a buffer at `UTILISATION_TARGET` (80 %), and resolves zone wall times (`zonedInstant`, DST gaps). `paper-match.ts` normalises leaf paper labels and catalogue components to `P<n>`. `priority.ts` scores each leaf (mastery estimate blending the self-rating prior with marks by attempt count, urgency floor 0.5, frequency, review due, soft prerequisite, nearest paper), assigns must/should/could bands per mode and picks the weak or strong loop. `feasibility.ts` computes must/full demand per subject from loop minutes and the taper, compares it with laid-out supply and returns the three honest states with calm headlines, tradeoffs and options. `high-yield-rank.ts` gains `paperFrequency` (N ≥ 6 well-tagged papers, n ≥ 3, per component when chosen, real session range). `build-study-plan.ts` gains `buildRoadmap()` (`PLAN_VERSION = 3`): tuple task ids, loops (diagnose → repair → recall → prove → review; strong: recall → prove → timed set), provisional steps after a diagnostic, spaced reviews clamped ≥ 2 days before the paper, timed papers only in a contiguous interval ≥ the paper with session ≥ 40, exams as commitments, `validateRoadmap()`. `task-actions.ts` is the reducer for start/complete/shorten/skip/defer/swap/checkin/pin/unpin, `replanToday` (protects done/pinned/started, writes a diff), `rolloverDay` (lazy, idempotent, defers at most one task once, re-branches provisional steps from the diagnostic result), single-level undo and the materialised today summary. ### Fix pass after the three reviews (2026-09-17, later)

_An adversarial code review, a trust audit of generated plans and a real-browser QA run (`scripts/verify-roadmap.mjs`) came back the same evening. Every blocker and major was applied, plus the minors that were cheap; what was skipped is listed with the reason. Every engine and reducer fix carries a `tsx` test._

**Engine (`lib/plan/`).**

- `availability.ts` — `layoutDay` never overshoots past `UTILISATION_MAX` (a 60-minute day lays 45, not 55; the third 10-minute interval of a 15+15+10 day stays in hand), and a long break that leaves no room for a slot degrades to a short one instead of ending the day. Utilisation across the fixture grid (three modes × three session lengths) is now 0.69–0.85 and the balanced/40 plan sits at 0.78; `build-study-plan.test.ts` pins the band.
- `build-study-plan.ts` — the loop-stall the trust audit called a blocker: a new topic is never opened in a slot shorter than a session while an open loop is waiting, a timed set that no slot can hold proves with one marked question (`fitStep`), and `loopStepsFor` swaps `timed_set` for `question` when the session is under 30 minutes, so the confident subject on 20-minute sessions reaches its marked questions (foundation/20: Physics 6 of 6 reached, was 0). `SUBJECT_TOUCH_EVERY_STUDY_DAYS` is enforced: an overdue subject (no task in the last three study days, never-touched counting from day one) takes any slot it can fill before the day's focus subjects, and the other live subjects may fill a slot the focus ones cannot; four subjects on 60-minute days now all get touched every three study days. A leftover slot stays with the subject that just used it, so day one no longer alternates subjects every ten minutes. Foundation opens one topic a day while a loop is open. A known-weak topic (three or more marked answers) opens on its repair rather than "this sets where you start"; `DIAGNOSE_WHEN_UNCERTAINTY_AT_LEAST` is 0.3 so one or two attempts always get the diagnostic. An empty signal list (a subject with no syllabus tree) falls back to the v2 lists and, failing those, fills the day with mixed sets that say `NO_TOPIC_INDEX_LINE` rather than one 25-minute set and "on track". Timed papers keep a marking allowance in hand (`paperMarkingMinutes`: 10 or a tenth of the paper), their objective says so, a mostly-weak subject sits none in the first third of its study days, and every paper and mixed set carries a `mode` evidence line (no task has an empty `why`). Taper reviews prefer proved loops, then topics with marked answers; a never-worked topic gets "check it against the mark scheme" with syllabus evidence only. The evening of a paper holds one short review, "only if you feel like it". IB objectives use marking-point wording. Headlines pluralise. `buildStudyPlan()` stamps `LEGACY_PLAN_VERSION` (2) so v2-shaped plans keep the rebuild offer.
- `feasibility.ts` — a topic counts as reached only when its marked question is on the calendar (`plannedTopics` = proved loops); `mustReachable` (must-cover loops that fit before the taper) is what "N of M reached" is measured against, `started` lists opened-but-unproved topics, a plan that proved fewer than the calendar could hold is `focused` with a tradeoff naming them, "left for later" replaces "after the must-cover ones are solid", a taper subject shows "Review only" and no later line, the 20-minute tradeoff says "no timed papers or sets", and the report carries `capacityMinutes / laidMinutes / studyDays` so the card's "in hand" is arithmetic.
- `task-actions.ts` — the undo snapshot covers every date a change reached (`otherDays`) plus `lastDiffDate`, `lastDiff` and `durationScale`, so undoing a defer removes the copy, undoing a rollover restores yesterday's entries, undoing a took_longer restores the scale, and the "Adjusted today" chip goes with the change it marked. Replans, rollovers and check-in effects write `plan.lastDiff`, so "See what changed" and Undo survive a page load. `structural` says when the revision moves: start, complete, skip and a plain check-in keep it (the QA's three 409s after "Start focus block" are gone). Deferred copies are built with `stripDestination` and hydrated afresh. Shorten and swap keep a started task started. `too_hard` inserts the refresh on any step with a topic; `was_busy` on a done task moves the topic's next open step today (the sheet opens after Done); a check-in on a task still to do completes it and records `task_completed` beside `task_checkin`; `availableFeels()` lists only the feelings the reducer would act on, and the sheet shows those. ## 10. Decisions after the design critique (2026-09-17)

Four independent reviews (learning science, scheduling, trust, codebase fit) attacked §1–§6 before implementation. What changed:

**Pedagogy.** The self-rating is a prior, never a verdict: a leaf with < 3 marked attempts always starts with a 10-minute diagnostic, the steps after it are `provisional`, and the daily rollover re-branches them (weak < 65 % → repair; else straight to the marked question). Loop steps are spaced (repair → recall waits a study day). The review gap is set by the marked result (`reviewGapDays`: 1/2/4/7 days) and clamped ≥ 2 days before the paper; the review task is retrieval-first. Every check-in feeling has a defined effect (`CHECKIN_FEEL_EFFECT`), applied as a diff with undo. Foundation finishes loops before widening; every live subject is touched at least every 3 study days; urgency has a floor of 0.5.

**Scheduling.** `availabilityDetail` is the only capacity input; the 7-array and `minutesPerDay` are derived for legacy columns. Capacity is wall-clock; supply is work minutes after layout; utilisation = Σ(work + breaks) / Σ capacity. Per-type minimums (`MIN_TASK_MINUTES`), a 10-minute floor for a study day, slots per free interval, breaks never at interval edges. Exams are commitments on their date (another subject's eve-review may still run after the paper ends). Spans cross midnight explicitly; windows may not; `zonedInstant` resolves DST gaps. Timed papers need one contiguous interval ≥ the paper and a session length ≥ 40. Task ids are tuple-based (`date-subject-topic-n`) and survive replans; rollover is lazy on read, idempotent, defers at most one task once, never stacks. Prerequisites are a soft scoring term only.

**Trust.** Frequency evidence needs N ≥ 6 well-tagged papers and n ≥ 3, computed per component when the student chose one, with the real session range (May/June 2024 → Oct/Nov 2025 today, never "2021–2025"); source is `indexed_papers` (tags are classifier output), confidence medium, copy "Set in n of the N … sittings MarkScheme has indexed". "Weak area" needs ≥ 3 attempts; 1–2 attempts is "recent practice". Bands are must/should/could. `on_syllabus` is the default evidence; `core_syllabus` is never emitted until a tree carries a flag. Objectives and explanations come from templates and numbers only; a privacy test asserts no scheme text leaves the server. Guilt copy is gone from `checkinLine`, the streak leaves every v3 surface, and a test forbids `behind / missed / streak / catch up` in nudges. Every Why sheet ends with `WHY_SHEET_FOOTER`.

**Codebase.** `WORK_KINDS` replaces classification-by-exclusion; `buffer` is never work. `strategy` is a new column (the `preparedness` check is not widened); a v3 plan stores both. Pools live in their own column; task/replan/undo routes return one day; `today_summary` is materialised; undo is a ~5 KB day snapshot. Task actions carry `revision` (409 on mismatch) and repeats are no-ops. The engine modules import nothing server-only and are tested without the react-server condition. The Study Mode chip fetches only when signed in, caches per day, and reserves its height.
